> **维护对象**：任何 AI 助手和人类读者。
> **目的**：记录每一次对代码或文档有实际变更的事项，防止上下文在长会话或跨会话中丢失。

## 维护规范

1. **每个条目必须有状态**：🟢 已完成 / 🟡 进行中 / 🔴 废弃
2. **废弃条目处理**：确认无历史参考价值后删除；有保留价值的（如设计方向曾被尝试后放弃）改为废弃态并注明原因
3. **新条目追加**：按时间顺序，新增在同 Phase 节末尾或创建新节
4. **内容底线**：做什么 + 为什么 + 结果。不记录纯讨论/调研，只记录对代码或文档产生了实际变更的事项
5. **时效性**：进行中的条目超过 7 天无更新，主动询问是否仍有效或标记废弃

### 🟢 iOS 平台迁移：提醒链路平台化改造

- **做什么**：项目由 Android-only 扩展为 Android + iOS 双平台。新增 `PlatformCapabilities` 平台能力探测，把 `ReminderScheduler` 接口从 `reminder_coordinator.dart` 拆出独立文件，新增 `AndroidReminderScheduler`（原 AlarmManager 逻辑原样迁移）和 `IosReminderScheduler`（`zonedSchedule` + `DateTimeComponents.time` 每日重复本地通知）。
- **为什么**：iOS 没有「在指定时刻唤起进程执行代码」的能力，本地通知的标题和正文在调度那一刻就被系统冻结，触发时 App 进程不会启动。因此 Android 侧「到点联网拉考勤再拼实时文案」的链路在 iOS 上无法复制，只能降级为固定文案。按项目「相似相溶」要求，平台判断集中到 `PlatformCapabilities`，不散落各文件；按「拓展预留」要求，能力以 `supportsExactBackgroundAlarm` 这类语义命名暴露，而非直接暴露平台名。
- **结果**：`ReminderCoordinator` 行为和接口完全不变，仅默认实现改为按平台选择，因此其原有 4 个测试一行未改即通过。修复 3 处 iOS 上的真实缺陷：`NotificationService.initialize()` 无条件调用 `AndroidAlarmManager.initialize()`（iOS 必经此路径）、「测试生效」中的 `exit(0)`（Apple HIG 禁止 App 主动退出，iOS 改为预约本地通知并提示回桌面）、缺失 `NSPhotoLibraryAddUsageDescription`（保存打卡照片时会直接崩溃而非弹权限框）。设置页三处 Android 专属文案（自启动、省电优化）与「权限设置」入口按平台分支。`checkAllPermissions()` 在 iOS 上不再把系统不支持误报为用户拒绝。

- **为什么**：静态审查能在真机验证前排掉一批必然出错的路径，避免真机调试时被低级问题干扰。
- **结果**：
  1. **（严重）** `NotificationService.requestNotificationPermission()` 在非 Android 分支直接 `return true`，从不向 iOS 申请授权。用户拒绝通知后 `ReminderCoordinator` 仍判定已授权、界面显示「提醒已开启」，而通知永不送达，属静默失效。改为调用 `IOSFlutterLocalNotificationsPlugin.requestPermissions()`。
  2. `login_screen` 未设置 `sharedCookiesEnabled`（iOS 专属，默认 false），直接影响 `www_token` 能否稳定被 `CookieManager` 读取，已开启。
  3. viewport 原在 `onLoadStop` 注入，即页面渲染完之后；WKWebView 首屏后再改 `initial-scale` 不一定触发重新布局。改为 `initialUserScripts` + `AT_DOCUMENT_START`，并在 `DOMContentLoaded` 重新应用一次（防止页面自身覆写）。
  4. 上述改动后 `onLoadStop` 中重复的 viewport 逻辑已删除，避免同一职责两处维护。
- **补充**：新增 `_checkLayout()` 布局自检，输出 `scrollWidth / innerWidth / overflow / scale / viewport` 实测值，用客观数据替代肉眼判断 iOS 排版是否溢出。
- **验证**：`flutter analyze` 无问题，`flutter test` 107/107 通过。

### 🔴 环境踩坑记录：Xcode 26 平台组件（重要）

以下为本次迁移在环境侧消耗时间最多的问题，记录以避免重蹈覆辙。

- **`flutter build ios` 失败时仍返回退出码 0**。判断构建结果必须查看输出内容与 `build/ios/` 产物，**不能依赖退出码**，此坑先后误导两次。
- **`xcodebuild -showsdks` 显示 `iphoneos26.5` 不代表可以构建**。Xcode 26 把平台拆为可下载组件，SDK 文件存在但组件未注册时，构建仍报 `iOS 26.5 Platform Not Installed`。已用 clang 实编译（C 与 Objective-C + UIKit 均通过）确认 SDK 本身完好，问题纯在 DVT 平台注册。
- **`xcodebuild -downloadPlatform iOS` 只下载模拟器运行时**，不含真机平台支持。真机所需的是 Components 中 `iOS 26.5.1 + iOS 26.5 Simulator` 整个组件。
- **中途终止 `-downloadPlatform` 会留下已下载但未挂载的僵尸镜像**，导致后续安装报 `SimDiskImageErrorDomain Code=5 Duplicate of <UUID>`。清理方式：`xcrun simctl runtime delete <UUID>`。
- **非交互 shell 中执行 `-downloadPlatform` 无法弹出管理员授权**，会停在「下载完成但装不上」。应通过 Xcode GUI 的 Settings → Components 安装。
- **`-sdk iphoneos` 只能绕过 `-showBuildSettings` 的目标解析**，真正 `build` 仍需 destination，无法作为规避手段。
- **查看 Apple 下载进度**：`xcodebuild` 用 `\r` 覆盖同一行输出，`tail` 看不到内容。用 `tr '\r' '\n' < 文件 | tail` 可读出真实百分比；暂存目录为 `/System/Library/AssetsV2/downloadDir/`，`du -sh` 可测实际进度。

### 🔴 BOSS 系统对接的关键事实（重要）

- **系统地址是 `boss.hoteamsoft.com` 而非 `coplan.hoteamsoft.com`**。两者是同一套平台的不同实例（首页大小 93701 vs 93707），用户账号只在 boss 上有效。统一使用 https（实测可用），避免 iOS ATS 明文流量限制。
- **企业微信入口不可用**：`/EntWeChat/workReport/` 系列页面靠 OAuth `code` 换取身份并存入 `sessionStorage.windowPara`，该 code 一次性且约 5 分钟过期，APP 无法自行生成。已提供「粘贴链接打开」作为变通（用户在企业微信内复制带 code 的链接后粘入）。
- **填报表单没有独立网址**：表单是首页工具栏「新增工作日志」弹出的面板，导出显示 url 恒为首页。
- **控件 id 每次加载都变**：实测同一字段 `guid161_TextBox` → `guid220_TextBox`（整体偏移 +59）。因此自动填充必须按标签文字定位，按 id 写死会把内容填进错误字段。
- **下拉框与 autoCombox 是自研伪控件**（`input.readonly` + 隐藏真实值），直接改 `value` 只改显示不改内部状态，保存时会提交空值，故自动填充主动跳过并提示用户手动选择。
- **不自动点击「保存」**：面向公司真实系统，填充后必须由用户核对再提交，已用测试断言脚本中不含点击动作。
- **已修复缺陷**：打开表单时同时执行 `element.click()` 与 `jQuery(el).trigger('click')` 会弹出两个重复表单（实测 fieldCount 由 37 涨到 130，出现 4 套重复表单），已改为只点一次。
