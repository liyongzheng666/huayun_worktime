# 踩坑记录

> **用途**：记录排查耗时超过 10 分钟、或曾导致错误结论的问题。
> **收录标准**：现象具有欺骗性、原因不直观、或同类问题还会再遇到。
> 单纯的语法错误、一次就改对的问题不收录。
> **每条格式**：现象 → 真实原因 → 对策。

相关文档：`docs/操作记录.md`（变更流水）、`docs/android_code_review.md`（审查记录）、`docs/hikiot_api_reference.md`（海康接口）。

## 一、iOS 工具链与构建

### 1.1 `flutter build ios` 失败仍返回退出码 0 ⚠️ 高频

**现象**：命令退出码 0，脚本判定成功，实际什么也没构建出来。

**原因**：Flutter 的 iOS 构建在部分失败路径下不置错误码。

**对策**：**永远不要用退出码判断 iOS 构建结果。** 必须同时检查：
- 输出中是否出现 `Failed to build iOS app`
- `build/ios/iphoneos/Runner.app` 是否真实存在

本次迁移中此坑先后误导两次，第二次已经对外宣称"编译通过"后才发现产物为空。

### 1.2 `xcodebuild -showsdks` 列出 SDK ≠ 可以构建

**现象**：`xcodebuild -showsdks` 显示 `iOS 26.5 -sdk iphoneos26.5`，据此判断真机可编译，实际构建报 `iOS 26.5 Platform Not Installed`。

**原因**：Xcode 26 把平台拆成了可下载组件。SDK 文件存在，但组件未在 Xcode 的平台注册库中注册时，构建系统仍拒绝。

**对策**：判断是否可构建，用 `xcodebuild -showdestinations -scheme X -workspace Y`，看有没有 `Available destinations`。没有就是不可构建，不管 SDK 列表怎么显示。

### 1.3 iOS SDK 只有 70 MB 不代表它是存根

**现象**：`iPhoneOS.sdk` 仅 70 MB，对比 `MacOSX.sdk` 261 MB，据此判断 SDK 是占位符。

**原因**：**判断错误**。SDK 内只有头文件和 `.tbd`（文本形式的动态库存根），不含二进制实现，体积本就不大。该 SDK 有 277 个框架，是完整的。

**对策**：验证 SDK 是否可用要**实际编译**，不能看体积：

```bash
SDKP=$(xcrun --sdk iphoneos --show-sdk-path)
printf '#import <UIKit/UIKit.h>\nint main(){return 0;}\n' > /tmp/t.m
xcrun --sdk iphoneos clang -arch arm64 -isysroot "$SDKP" -fmodules -c /tmp/t.m -o /tmp/t.o
```

### 1.4 `-downloadPlatform iOS` 只下载模拟器运行时

**现象**：执行后仍无法构建真机。

**原因**：该命令下载的是 `iOS xx Simulator` 运行时。真机所需的平台支持在 Components 里是 `iOS 26.5.1 + iOS 26.5 Simulator` 这一整个组件。

**对策**：真机平台支持只能通过 **Xcode GUI → Settings → Components** 安装。命令行装不全。

### 1.5 中途终止下载会留下僵尸镜像

**现象**：重新下载完成后安装失败，报
`SimDiskImageErrorDomain Code=5 "Duplicate of <UUID>"`。

**原因**：上次被终止的下载其实已完成落盘，状态为 `Ready` 但未挂载。新镜像安装时判定重复。

**对策**：
```bash
xcrun simctl runtime list          # 查看，注意 Unusable / Ready 状态
xcrun simctl runtime delete <UUID> # 删除僵尸镜像后重装
```
**更好的对策是不要中途终止这类下载。** 本次因终止一次，连锁导致后续多轮失败与约 8.5 GB 重复下载。

### 1.6 非交互 shell 无法完成需要授权的安装

**现象**：`xcodebuild -downloadPlatform iOS` 显示下载 100%，随后卡在 `Installing...` 或直接失败。

**原因**：挂载镜像需要管理员授权，非交互 shell 弹不出授权对话框。

**对策**：这类操作走 Xcode GUI。

### 1.7 `-sdk iphoneos` 不能绕过 destination 解析

**现象**：`-showBuildSettings` 加 `-sdk iphoneos` 可以正常返回，据此以为能绕过平台检查。

**原因**：只有 `-showBuildSettings` 不需要 destination；真正执行 `build` 仍要解析，报 `Found no destinations for the scheme`。

**对策**：此路不通，老实装平台组件。

### 1.8 Apple 的下载进度用 `\r` 覆盖同一行

**现象**：`tail -f` 输出为空，误以为没有进度信息。

**原因**：进度用回车符覆盖同一行，整个输出是一个超长单行。

**对策**：
```bash
tr '\r' '\n' < 输出文件 | tail        # 读出真实进度
du -sh /System/Library/AssetsV2/downloadDir/   # 直接看暂存目录大小
```
本次因不知此法，绕道用磁盘增量估算，还估错了（把「已续传」误判为「从头下」）。

### 1.9 Xcode 更新后许可需重新接受

**现象**：`flutter doctor` 持续报未接受许可，但记忆中已经接受过。

**原因**：许可记录按版本号存储。查：
```bash
defaults read /Library/Preferences/com.apple.dt.Xcode IDEXcodeVersionForAgreedToGMLicense
```
显示 `26.2` 而实际 Xcode 是 `26.6` → 需重新接受。

**对策**：`sudo xcodebuild -license accept`。注意用 `&&` 串联多条 sudo 命令时，这一步失败会静默中断后续命令。

### 1.10 代码签名会弹钥匙串授权，无人值守时卡死

**现象**：构建进程存活、CPU 0%、`Runner.app` 已生成但命令不返回，持续数小时。

**原因**：`codesign` 访问钥匙串私钥触发 GUI 授权框，等待用户输入。

**对策**：
- 诊断：`ps aux | grep SecurityAgent`，同时看 `codesign` 是否 0% CPU
- 首次授权时点**「始终允许」**，否则每个 framework 都会弹一次

本次此坑导致一次构建耗时显示为 `25573 秒`。

### 1.11 `flutter install` 每次先卸载，会清空 App 数据 ⚠️ 高频

**现象**：每次安装后都要重新登录、重新配置。

**原因**：`flutter install` 的实现是先 uninstall 再 install。

**对策**：改用标准 iOS 升级语义，**保留应用容器**：
```bash
xcrun devicectl device install app --device <UDID> build/ios/iphoneos/Runner.app
```
本次因一直用 `flutter install`，让用户反复重新登录了七八次，属可完全避免的浪费。

### 1.12 Release 构建抓不到 `flutter logs`

**现象**：`flutter logs` 输出为空。

**原因**：Release 构建不启用 Dart VM 服务，`flutter logs` 无从附加。`debugPrint` 只进 iOS 系统日志。

**对策**：
- 需要日志又不想清数据 → **把诊断信息复制到剪贴板**，由用户粘贴回传（本项目采用此法）
- 或改用 Debug 构建（代价：数据被清、断开连接后 App 无法独立运行）

### 1.13 Debug 与 Release 共用同一产物路径

**现象**：先构建 Debug 再 `flutter install --release`，装上去的是 Debug 版。

**原因**：两者都输出到 `build/ios/iphoneos/Runner.app`，后构建的覆盖先构建的。体积可辨（Debug 约 144 MB，Release 约 27 MB）。

**对策**：切换构建类型后重新构建目标类型，安装前用 `du -sh` 确认。

## 二、iOS 代码适配

### 2.1 Android 专属插件被无条件调用

**现象**：iOS 上初始化即崩。

**原因**：`NotificationService.initialize()` 无条件调用 `AndroidAlarmManager.initialize()`，而 iOS 路径必经此方法。

**对策**：平台判断集中到 `PlatformCapabilities`，按**能力**而非平台名暴露（`supportsExactBackgroundAlarm` 而非 `isAndroid`），避免判断散落各处。

### 2.2 `exit(0)` 违反 Apple 规范

**现象**：Android 的「测试提醒」流程用 `exit(0)` 退出 App 以验证后台唤醒。

**原因**：Apple HIG 明令禁止 App 主动退出，审核会拒，用户观感等同闪退。

**对策**：iOS 改为预约本地通知并提示用户回桌面等待。

### 2.3 缺少权限描述直接崩溃，而非弹权限框

**现象**：保存打卡照片时 App 直接退出。

**原因**：`Info.plist` 缺 `NSPhotoLibraryAddUsageDescription`。iOS 对缺失用途描述的行为是**终止进程**，不是拒绝权限。

**对策**：任何触碰隐私 API 前先补齐 `Info.plist` 描述。

### 2.4 权限申请被无条件放行导致静默失效 ⚠️ 严重

**现象**：iOS 上界面显示「提醒已开启」，但通知永远不来。

**原因**：
```dart
if (Platform.isAndroid) { ...真正申请... }
return true;   // iOS 从不申请，直接返回「已授权」
```
用户拒绝通知后，上层仍判定已授权、正常调度，无任何报错。

**对策**：iOS 走 `IOSFlutterLocalNotificationsPlugin.requestPermissions()` 真实申请。
**通用教训**：「平台不支持」不能简化为「返回成功」，否则失败会变成静默的。

### 2.5 iOS WKWebView 默认不共享 Cookie

**现象**：登录态不稳定。

**原因**：`sharedCookiesEnabled` 是 iOS 专属设置，**默认 false**。

**对策**：涉及登录的 WebView 显式设为 `true`。

### 2.6 viewport 注入时机太晚

**现象**：页面先闪现错误排版。

**原因**：在 `onLoadStop` 注入，此时页面已渲染完；且 WKWebView 首屏后再改 `initial-scale` 不一定触发重排。

**对策**：改用 `initialUserScripts` + `AT_DOCUMENT_START`，并在 `DOMContentLoaded` 再应用一次（防页面自身覆写）。

**配套**：不要靠肉眼判断排版，注入自检脚本输出实测值：
```js
{ scrollWidth, innerWidth, overflow, scale, viewport }
// overflow > 0 即横向溢出
```

### 2.7 `UserScript.forMainFrameOnly` 默认为 true ⚠️ 严重

**现象**：注入的抓包钩子一条请求也抓不到。

**原因**：门户型系统的业务页跑在 iframe 中，而该参数默认只注入主框架。

**对策**：`forMainFrameOnly: false`；**读取时也要递归遍历 `window.frames` 汇总**，只读主框架同样会漏。

**2026-08-06 补记：这条只改对了一半，代价很大。**

当时只在「导出抓包」「清空抓包」两处做了递归，而真正干活的六个脚本
（提交、会话探测、提取常量、扫描常量、单日工时、整月工时）全都还是
`window.<store>`，即只读主框架。后果是：

- 用户明明打开了「我的工作日志」列表，扫描却永远报「找不到项目信息」——
  因为列表跑在 iframe 里，数据落在 iframe 那份 store，而我们读的是主框架那份；
- 由此误判「BOSS 是有状态 SPA，外部脚本无法可靠驱动」，连试三条自动发现路径
  全部失败，最后退化成让用户手工填三个内部 ID（见 3.10 与四、判断失误复盘）。

**根因不是 BOSS 难驱动，是我们扫的地方根本不是数据在的地方。**

现已把 `bossCaptured()`（递归汇总所有同源 frame 并按 `at` 排序）收口到
`BossSessionScript`，六处统一走它，并有测试断言「脚本正文里不得直接出现
存储名」。多个 frame 的记录时间上交错，**汇总后必须按抓取时刻排序**，
否则「从后往前取最新一条会话」会取到更旧的那条。

### 2.8 依赖升级导致 API 形态变化

**现象**：`FilePicker.platform.pickFiles(...)` 编译报错。

**原因**：`file_picker` 11.x 改为静态方法 `FilePicker.pickFiles(...)`。

**对策**：加依赖后先看包内 `lib/` 的实际签名，不要凭记忆写。


### 2.9 系统字体放大会撑爆固定 Row ⚠️ 高频

**现象**：数字被横向切掉。实测 `43.54 / 168.00h` 显示成 `43.54 / 168.0(`、`53.12%` 显示成 `53.12`、日历格子里的 `11.10` 变成 `11.1(`，个别情况下第二行内容还会溢出到格子外压住下一行。

**原因**：用户开启了**系统字体放大**。`Row` 里若干定宽子项（图标、标签、徽章、数字）宽度全都跟着字号增长，而 `Row` 放不下时**不会收缩，直接溢出裁掉**。

判别线索：同一组卡片里，**没有徽章的那一行显示正常、有徽章的被切**——说明是宽度问题而非数据问题。

**对策**（按场景选）：
- 多个并列元素 → 换 `Wrap`，放不下自动换行，横向结构性不可能溢出
- 单个大号数字 → 套 `FittedBox(fit: BoxFit.scaleDown)`，宁可缩小也不裁切
- 行内可省略的说明文字 → `Flexible` + `TextOverflow.ellipsis`，优先保证右侧控件不被挤出屏幕

**教训**：这个坑先后被用户指出三次，前两次都只修了他截图指到的那一处，没有推及同页其它卡片。**同一成因的问题要一次扫干净**——可用脚本粗筛「Row 内有多个数字 Text 且无 Expanded / Flexible / Wrap 保护」的位置。

**注意**：不要用缩小字号来解决用户明确要求「醒目」的内容，那是在对抗用户的辅助功能设置。应改排布（如把数字挪到独立一行，反而能放更大）。

## 三、BOSS（华天）系统对接

### 3.1 URL 里的 `code=` 是一次性 OAuth 码

**现象**：把用户给的链接写进代码，一直无法访问。

**原因**：`code` 是企业微信 OAuth 授权码，**一次性、约 5 分钟过期**。页面用它换取身份存入 `sessionStorage.windowPara`。

**对策**：不可硬编码。可提供「粘贴链接打开」，由用户在企业微信内复制新鲜链接后粘入。

### 3.2 控件 id 每次加载都变 ⚠️ 严重

**现象**：按 id 写的自动填充第二次就填错字段。

**原因**：实测同一字段两次加载的 id 为 `guid161_TextBox` → `guid220_TextBox`，整体偏移 +59。

**对策**：**按标签文字定位**。发现方法：连续导出两次页面结构做对比——这个验证花两分钟，能避免把工作内容填进工时框且不易察觉。

### 3.3 自研伪控件不能直接赋值

**现象**：下拉框显示已改，保存后提交的是空值。

**原因**：下拉与 autoCombox 是 `input.readonly` + 隐藏真实值的自研控件，改 `.value` 只改显示，框架内部状态不变。

**对策**：识别 `readOnly` 或 class 含 `readonly` 时**主动跳过并提示用户手动选**。宁可少填，不可填错。

### 3.4 表单没有独立网址

**现象**：找不到可直达的填报页 URL。

**原因**：导出显示 `url` 恒为首页——表单是首页工具栏「新增工作日志」弹出的面板。

**对策**：只能模拟点击，或改用报文提交（本项目最终选择后者）。

### 3.5 原生 click 与 jQuery trigger 双触发

**现象**：`fieldCount` 从 37 涨到 130，页面出现 4 套重复表单。

**原因**：
```js
best.click();
if (window.jQuery) window.jQuery(best).trigger('click');  // 又触发一次
```
原生 click 已能触发 jQuery 绑定的处理器，补发等于点两次。

**对策**：只点一次。

### 3.6 CSV 的「无」要提交为空串

**现象**：类型为「设计」时字段值不对。

**原因**：CSV 中项目阶段/阶段活动写作 `无`，但实测该类型下报文提交的是 `""`。

**对策**：`无` → `""` 归一化，有测试锁定。

### 3.7 LOGTYPE 编码表

从表单下拉的 `DataSource` 提取，实测有效：

| 编码 | 类型 | 编码 | 类型 | 编码 | 类型 |
|---|---|---|---|---|---|
| 1 | 会议 | 8 | 质量 | 15 | 市场 |
| 2 | 培训 | 9 | 文案 | 16 | 财务 |
| **5** | **研发** | **10** | **设计** | 17 | 人力 |
| 6 | 实施 | 11 | 维护 | 18 | 管理 |
| **7** | **测试** | 12 | 售前 | 19 | 文档 |
| | | 13/14 | 营销/经管 | 20 | 其他 |

### 3.8 列表接口是有状态视图 ⚠️

**现象**：用与抓包完全一致的参数调 `GetDataGridList`，返回 `200` 但 `Rows: []`。

**原因**：该视图必须先由 `GetTitle` 在服务端建立查询上下文。单独调用时服务端不知道在查什么。

**对策**：不要自行构造这类查询。**让页面自己去查，脚本只负责收割响应。**

### 3.9 同一数据有两种响应形状 ⚠️

**现象**：用户打开了日志列表，扫描仍报「找不到项目信息」。

**原因**：只按详情形状写了正则：
```
详情：  "PROJECTID":"PROJECT_xxx"                              ← 打开某条日志
列表：  "ColName":"PROJECTNAME", …, "ColValue":"PROJECT_xxx"   ← 打开列表
```
列表形状里根本没有 `PROJECTID` 这个字面量。

**对策**：两种形状都要覆盖，并用真实响应片段写测试。BOSS 响应是多层转义 JSON，正则需用 `\\*"` 容忍任意转义层数。

### 3.10 抓包缓冲过小会挤掉业务数据 ⚠️

**现象**：诊断显示 `capturedCount: 40`，据此认为「数据是满的」，判断方向因此跑偏。

**原因**：**40 正是当时设的上限**。而 BOSS 经典首页自身加载就会发十几到几十个请求，缓冲一满，后续真正需要的业务响应就被挤出去了。

**对策**：
- 缓冲设大（本项目改为 150）
- **诊断里的计数值等于上限时，要先怀疑是截断而非真实数量**

**2026-08-06 补记：这次的判断其实也是错的，只是错得没那么明显。**

40 确实等于当时的上限，但真正的原因是**只读了主框架**（见 2.7）：主框架里
本来就只有首页自身那几十个请求，业务数据全在 iframe 那份 store 里。
把上限从 40 提到 150 之后问题依旧，因为缓冲多大都不影响「读错了地方」。

**教训**：找到一个能自圆其说的解释，不等于找到了原因。改完之后现象没变，
就说明解释是错的，此时应该回头质疑前提，而不是继续在同一个方向加码。

### 3.11 会话筛选条件不能包含自己要设的字段

**现象**：刚登录时取不到会话，必须先在页面上操作一次。

**原因**：
```js
if (para.UserID && para.ServiceUri) return para;   // 错
```
`ServiceUri` 是**我们自己要设的值**，拿它当筛选条件是逻辑错误。登录后首页自动发的 `CheckUserUnReadMessage` / `GetIntervals` 都不带该字段，但 `para` 是完整的。

**对策**：只用 `UserID` 判断。已加测试防止改回去。

**2026-08-06 补记**：当时四处 `findPara` 只改了三处，漏了「整月工时」那一处。
表现是刚登录时同步整月报「未捕获到会话」、而单日查询正常——同一件事两种结果，
极难排查。现已收口到 `BossSessionScript.sessionPreamble()`，全项目只有一份实现。

**通用教训**：同一段逻辑抄了 N 份，就等于同一个 BUG 要修 N 次，而人一定会漏。
`findPara` 抄了 4 份、「拼报文 + 逐层解响应」抄了 3 份，
这两个漏修（本条与 2.7）都直接源于此。

### 3.12 凭据明文出现在每个业务请求体里 🔴 安全

**现象**：抓包中每条请求的 `para` 都含 `"Password":"..."`。

**风险**：该值等同登录凭据。若把会话上下文存进 App，等于本地明文保存密码。

**对策**：
- **不保存会话上下文**，只在 WebView 内就地复用页面刚发出的请求的 `para`
- 只持久化业务标识（项目 ID、审核人 ID），不碰凭据
- 已加测试断言脚本中不得出现 `Password` / `LoginID`
- 已建议用户更换该密码

### 3.13 提交接口不做幂等 🔴 数据安全

**现象**：同一天可提交多条，重复提交不报错。

**风险**：双击按钮、或自动与手动提交并发，会静默产生重复日志。

**对策**：
- 提交加互斥锁
- 提交前用 `GetWorkHours` 查当天已填工时，>0 时在确认框显式警示
- 按钮文案改为「**仍要**提交」，让重复成为需刻意确认的动作
- **查询失败时不能当作「未填报」**，要显示「未能确认」——「未知」与「为零」是两回事


### 3.14 网格里的列名不是你以为的那个 ⚠️ 严重

**现象**：诊断显示 `projectIdSeen / auditorSeen / preferredSeen` 全为 true，即数据确实抓到了，但解析始终失败。

**原因**：正则按 `ColName":"PROJECTNAME"` 找项目，而 `GetHisWorkLogList` 返回的网格里**根本没有这个列名**。真实形状是：

```
ColName:"PROJECTID"    ColText:"面向比亚迪…项目-自筹"  ColValue:"PROJECT_899d…"
ColName:"PROJECTCODE"  ColText:"PROJECT_75e0…"        ColValue:"PROJECT_75e0…"
ColName:"AUDITOR"      ColText:"杨亚伦"                ColValue:"USERINFO_891c…"
```

即**项目名在 `PROJECTID` 列的 ColText，项目 ID 在同列的 ColValue**。另有 `XXX$DBValue` 伴生列，其 ColText 存原始标识、ColValue 为 null。

**对策**：
- 不要凭字段语义猜列名，**先把真实响应打出来看**。为此诊断增加了命中片段取样。
- 网格数据**按行解 JSON，不要用正则跨行匹配**：一次响应含多行历史日志，正则很容易把第 1 行的项目和第 5 行的审核人拼在一起，得到一份看似合理实则错误的配置。
- 同一列里标识可能在 ColText 也可能在 ColValue，两边都试并以前缀（`PROJECT_` / `USERINFO_`）判定谁是真正的标识。

### 3.15 找服务名比扫响应内容可靠得多 ⚠️

**现象**：连续三轮扫抓包响应找项目信息，全部失败。

**原因**：一直在猜「数据长什么样」，却从没查过「页面调了哪些服务」。BOSS 所有业务共用 `/Base/BaseService.asmx/DataService`，靠请求体里的 `para.ServiceUri` 区分，**36 条抓包里每条的服务名都在手上，却一眼没看过**。

**对策**：诊断输出服务清单——每个 `ServiceUri` 的调用次数、**吃哪些业务参数**（只取参数名，值里有 `Password`）、响应是否含 `PROJECT_` / `USERINFO_` / `WORKLOG_`、是否被截断。一张表就定位到了 `InforCenter.WorkReport.ProjectService.GetHisWorkLogList`。

**重放技巧**：`ViewName` / `ParaList` / `CustomViewFilterString` 这类参数依赖页面上下文，猜不出来。**原样复用页面自己发过的那次请求的内层 para 再发一遍**，即可拿到最新数据，同时绕开「这个视图是否有状态」的问题；重放失败再退回已抓到的响应。

### 3.16 「我的工作日志」是日历式，不点进某天不发请求

**现象**：让用户「打开我的工作日志列表」，抓包里始终没有日志数据。

**原因**：该页是日历，每天的日志单独隔离加载。停在日历上不点进具体日期，页面不会发出加载详情的请求。

**对策**：引导必须精确到「点开任意一个已填过的日期」。也说明日志与工时同为按日期取，因此可以配合已有的逐日 `GetWorkHours` 定位最近一条日志。


### 3.17 「没同步过」不能当成「没填报」⚠️ 已重犯一次

**现象**：周条上整个月的工作日全被标成红色「待补交」，而这些日子实际早已提交。

**原因**：`loadBossHours(monthKey)` 在**从没同步过**的月份同样返回空表，与「同步过但当天没填」无法区分。红点条件「已过去 + 有打卡 + BOSS 无记录」于是在未同步月份全部成立。

**对策**：
- 存储层增加 `hasBossHoursSynced(monthKey)`，按 key 是否存在判断，把「不知道」与「没有」分开。
- 只有确实同步过才敢下「未提交」的结论；未同步时不标红，并**明确显示「提交状态未知」**——此时还摆着一套颜色图例，会让人以为显示是准的，比不显示更糟。

**这是重犯**：3.13 已经写过「查询失败时不能当作『未填报』，要显示『未能确认』——『未知』与『为零』是两回事」，月历页的单日详情也已按此处理（未同步的日期不显示 BOSS 行）。把同一份数据搬到周条时又漏了一次。

**通用检查**：任何「缺省值＝空/零」的数据源，接入新界面时都要先问一句——**这个空是「确认没有」还是「还没查过」？** 两者若在 UI 上同形，就是误报的温床。

### 3.18 截断过的工时反推分钟，四舍五入会差一分钟

**现象**：「距离 0.1 刻度还差几分钟」的提示，在少数工时上整条差一分钟（该报 3 分钟却报 4 分钟）。

**原因**：项目里的工时一律是「分钟 ÷ 60 再截断两位小数」的结果，**截断永远让数值偏小**。69 分钟存成 1.14 小时（真值 1.15），`(1.14 * 60).round()` 回来是 68 分钟。全量枚举 24 小时内每一分钟，1441 个值里有 36 个会错。

**对策**：向上取整，并减去极小量抵消浮点误差：

```dart
static int hoursToMinutes(double hours) => (hours * 60 - 1e-6).ceil();
```

减 `1e-6` 是防止 693.0 这类刚好落在整数上的值被浮点误差抬成 694；不减的话反而多错一批。

**通用检查**：**任何截断过的值都不可逆**，别用四舍五入去「还原」它。要么保留原始整数量纲（这里是分钟），要么按截断的方向反向补偿。顺带一提，0.1 小时恰好是 6 分钟整，改用整数分钟做刻度运算，还能一并绕开 0.1 在二进制下不可精确表示的问题。

## 四、判断失误复盘

以下不是技术坑，是本次排查中的方法问题，价值更高。

| 失误 | 后果 | 教训 |
|---|---|---|
| 终止第一次平台下载 | 僵尸镜像 → 重复下载 8.5 GB → 多轮失败 | 大文件下载不要中途终止 |
| 「SDK 存在 = 能构建」 | 白跑一次构建 | 能力判断要**实测**，不能看现象推断 |
| 「70 MB = 存根」 | 方向跑偏 | 体积不是完整性的证据 |
| 用 `flutter logs` 抓 Release 日志 | 白等一轮 | 先确认工具的前提条件 |
| 把 `capturedCount: 40` 当作「数据充足」 | 连续两轮方向错误 | **计数等于上限时先怀疑截断** |
| 一直用 `flutter install` | 用户反复重新登录七八次 | 选工具前看清副作用 |
| 反复尝试自动发现项目信息 | 耗费用户四轮时间 | **失败两次后就该换方案**，手工配置一次是更诚实的选择 |
| 把「扫不到项目信息」归因为 BOSS 难驱动 | 三条自动路径全废，退化成手工填内部 ID | **失败前先确认自己读的是不是数据所在的地方**，详见下方复盘 |

### 关于「自动发现项目信息」的二次复盘（2026-08-06）

这件事值得单独记，因为它同时踩中了上面好几条教训。

当时的结论是「BOSS 是有状态且菜单结构不透明的 SPA，外部脚本难以可靠驱动」，
于是放弃自动获取，改成让用户手工填 `PROJECTID` / `PROJECTCODE` / `AUDITOR`
三个内部标识。**这个结论是错的。**

真实原因是：所有取数脚本都只读主框架的抓包记录，而 BOSS 的业务模块跑在
iframe 里（见 2.7）。用户做的操作全都是对的，数据也确实抓到了，
只是我们一直在错误的地方找。

三次「失败」于是变成了三次假阴性，而每次失败又反过来强化了那个错误结论——
这是最危险的一种循环：**错误的前提让所有实验都失败，而失败又被当成前提正确的证据。**

**能打断这个循环的问题**：「如果我的假设是对的，那这个现象还应该同时出现什么？」
当时若问一句「用户明明打开了列表，那这条响应到底进没进 store」，
只要按 frame 分别数一下条数，一次就能定位。现在的诊断脚本正是按 frame 输出的。

### 贯穿始终的方法教训

1. **退出码、体积、计数这类间接信号都可能骗人**，关键结论要用直接证据（产物是否存在、实际编译、真实响应内容）。
2. **诊断信息要能区分失败原因**。只报成败无法定位——「请求被拒」「返回空行」「字段名不匹配」在最终结果上完全一样。本项目后期加的诊断脚本会输出 HTTP 状态、行数、首行列名，这才让问题一次定位。
3. **自动化尝试两次不成，应主动提出降级方案**，而不是继续加复杂度。
4. **改完之后现象没变，说明解释是错的**。此时要回头质疑前提，而不是在同一方向继续加码（见 3.10 补记）。
5. **同一段逻辑抄 N 份，就是同一个 BUG 修 N 次**，而人一定会漏。本项目两次漏修都源于此（见 2.7、3.11）。
